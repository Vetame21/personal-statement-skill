# Report Types

Structures are defaults; the assignment brief or department handbook always wins.

---

## Lab report

Based on the IMRaD pattern used by most university writing guides (e.g. Sheffield, Toronto, Melbourne, Princeton).

| Section | Contains | Check |
|---|---|---|
| Title | Specific: what was measured, on what | Not "Lab Report 3" |
| Abstract | Aim, method, key results with numbers, conclusion (150-300 words) | Written last |
| Introduction | Theory needed, aim/hypothesis | Ends with the aim |
| Materials & Methods | Equipment, setup, procedure, parameters | Repeatable; past tense; passive voice is fine ("the solution was heated") |
| Results | Data tables, graphs, calculations with units | No interpretation |
| Discussion | Meaning, comparison with theory/literature values, error analysis | Explains discrepancies, not just lists them |
| Conclusion | Was the aim met? | No new data |
| References, Appendices | Sources; raw data, sample calculations | One citation style |

Error analysis: name the error source, its likely direction (over/under), and size if possible; suggest a concrete improvement.

## Programming lab or assignment report

For courses like Java, C++, data structures or mobile development labs.

1. **Cover**: course, lab number and title, name, student ID, date.
2. **Objective**: what the lab practises (e.g. inheritance, recursion, file I/O).
3. **Problem statement**: the task in the student's own words, with requirements listed.
4. **Design**: approach, class diagram or flowchart, key data structures, why this design.
5. **Implementation**: key code excerpts with explanation (not the whole program), notable decisions, problems met and how they were solved.
6. **Testing**: test-case table (input, expected, actual, pass/fail), including edge cases (empty input, invalid input, boundaries).
7. **Results / proof**: screenshots of program runs, cropped and captioned; link to repository if allowed.
8. **Reflection / conclusion**: what was learned, what was hard, what could be improved. Specific, in the student's own voice.
9. **Appendix**: full source code (if required), build/run instructions.

Markers look for: requirements met, evidence of testing, understanding of the code (especially if AI tools were used), and clear proof that the program runs.

## Technical or project report

1. Executive summary (one page max): problem, solution, results, recommendation.
2. Introduction: background, objectives, scope.
3. Requirements / specifications.
4. Design: architecture, alternatives considered and why rejected.
5. Implementation: stack, main components, challenges.
6. Testing and evaluation: method, metrics, results, comparison with requirements or a baseline.
7. Discussion: limitations, risks, costs.
8. Conclusion and recommendations / future work.
9. References and appendices.

Group projects: add a contribution table (member, tasks, percentage) if the brief asks.

## Makalah

Common Indonesian course paper format (check the lecturer's template):

- **Bab I Pendahuluan**: latar belakang (why the topic matters, with sources), rumusan masalah (questions the paper answers), tujuan (one per question).
- **Bab II Pembahasan**: one sub-section per rumusan masalah, each argued with sources, not just definitions.
- **Bab III Penutup**: kesimpulan (one per question), saran.
- **Daftar Pustaka**.

Common mistakes: pembahasan that only copies definitions from several sources; conclusions that do not answer the rumusan masalah; sources from blogs without authors.

## Internship report (KP / magang)

1. Cover, approval page (signed by the company supervisor and lecturer if required).
2. Introduction: background, objectives of the internship, time and place.
3. Company profile: short (history, structure, the unit you worked in). No marketing copy.
4. Role and tasks: what you were asked to do.
5. Work done: projects in detail (problem, what you did, tools, result), with evidence (screenshots with confidential data removed).
6. Problems and solutions.
7. Lessons learned: technical and professional, specific.
8. Conclusion and suggestions (for the company and for the university program).
9. Appendices: logbook, certificates, letters.

Check confidentiality: ask what the company allows to be shown; blur or remove client data.

---

## Progress report

1. Aims of the project (reminder).
2. Work completed since the last report.
3. Results so far (with evidence).
4. Problems and how they are being handled.
5. Next steps and updated timeline.
6. Help or decisions needed from the supervisor.

Keep it short and factual; a table of planned vs actual milestones works well.
